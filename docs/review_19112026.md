## P1 : priorité haute

### 1. Tests unitaires en échec, job CI `Unit tests` rouge
- **Statut** : Corrigé (commit `c4ad3b2`, tests passent).
- Fichier : `internal/domain/workflow/run_budget_test.go`.
- Problème : les attendus sont faux, pas le code. Formule `sum(timeout) + n*2s + 30s`.
  - « one call 30s clamps to min 1m » : 30s + 2s + 30s = 1m02s, pas de clamp. Attendu 1m00s, obtenu 1m02s.
  - « zero timeout uses default 30s » : même calcul, obtenu 1m02s.
  - « many slow calls hit max 25m » : 20×60s + 20×2s + 30s = 21m10s. Le test écrit 20m40s.
- Fix : corriger les trois attendus (ou la formule si l'intention est différente, à trancher). Le commentaire « 30s + 2s + 30s = 62s → clamp to 1m » est lui-même faux.

### 2. Secrets de production distribués à tous les services (`compose.yaml`)
- **Statut** : Corrigé : `env_file` retiré de `api`, `worker`, `worker-scheduler` ; env explicite. `JOB_SEAL_PRIVATE_KEY` seulement dans `worker-calls`.
- Fichier : `compose.yaml:29,45,59` (`env_file: [.env]` sur `api`, `worker-scheduler`, `worker`).
- Problème : `.env` contient `JOB_SEAL_PRIVATE_KEY`, `SECRETS_ENCRYPTION_KEY`, identifiants Kafka et stockage. La séparation « scheduler scelle, seul worker-calls ouvre » est annulée.
- Scénario : compromission de `api` ou du scheduler → déchiffrement des secrets de jobs et usage de n'importe quel compte Kafka.
- Fix : `environment:` explicite par service. Retirer `JOB_SEAL_PRIVATE_KEY` de tout service sauf `worker-calls`. Compte Kafka par service.

### 3. Rate limit partagé derrière Caddy
- **Statut** : Corrigé : `TRUST_PROXY=true` sur `api` (compose) → `ProxyHeader` X-Forwarded-For, trust des plages privées. Par défaut désactivé.
- Fichiers : `cmd/api/main.go` (`limiter.New`, clé `c.IP()`), `caddy/Caddyfile` (`reverse_proxy api:3000`).
- Problème : aucun `TrustProxy` ni `ProxyHeader` dans `cmd/` et `internal/` (vérifié). `c.IP()` = IP du conteneur Caddy.
- Scénario : un client dépasse `RATE_LIMIT_MAX` (100/min) → 429 pour tous les utilisateurs. Logs d'IP inutilisables.
- Fix : `ProxyHeader: fiber.HeaderXForwardedFor` avec `TrustProxy` restreint au réseau `edge`. Ou limiter par `user_id` après authentification (plus juste, à combiner).

### 4. Fuite de canal temps réel possible entre utilisateurs (à confirmer)
- **Statut** : Corrigé dans `centrifugo/config.json` (`allow_subscribe_for_client` retiré). **À valider en runtime avant déploiement** : la souscription doit toujours passer par le claim `channels` du token.
- Fichier : `centrifugo/config.json` : namespace `users` avec `allow_subscribe_for_client: true`.
- Problème : un client authentifié pourrait s'abonner à `users:<autre id>` et recevoir `workflow.*`, `incident.*`, `call.*`.
- Fix : test runtime (token de A, subscribe sur `users:B`). Si succès : retirer `allow_subscribe_for_client` et passer par des subscription tokens ou le claim `channels` côté `infrastructure/centrifugo/token.go`.

### 5. Proxy utilisateur contourne le contrôle SSRF
- **Statut** : Corrigé : proxy refusé par défaut, activable par `HTTP_ALLOW_PROXY=true` (worker-calls). Test ajouté.
- Fichiers : `internal/infrastructure/httpclient/executor.go` (`transport.Proxy = http.ProxyURL(proxy)`), `internal/contract/job.go:69` (`proxy_url` fourni par l'utilisateur).
- Problème : le dialer SSRF contrôle l'IP du proxy, pas la cible finale résolue par le proxy.
- Scénario : proxy externe contrôlé par l'attaquant relaie vers une cible bloquée par `IsBlocked` (métadonnées cloud, réseau interne).
- Fix : interdire `proxy_url` côté utilisateur, ou allowlist de proxies. Sinon, gérer CONNECT soi-même et appliquer `IsBlocked` sur la cible.

### 6. Erreur d'ID ignorée sur le chemin release de lease (dispatch)
- **Statut** : Corrigé : `errors.Join` sur les deux `uuid.Parse`, release abandonnée avec log d'erreur (`dispatch_due_runs.go`, `run_manual.go`).
- Fichiers : `internal/application/command/schedule/dispatch_due_runs.go` (`recordTimeout`, `release`, vers l. 332-334), `run_manual.go:177-178`.
- Problème : `uuid.Parse` ignoré. Un Nil donne `state == nil`, le lease n'est jamais libéré, jusqu'à expiry.
- Fix : retourner l'erreur. Les chemins `record_result` et `record_call_progress` sont déjà protégés par `Validate`.
